# 实测记录：requirement-forge

测试时间：2026-10-22。用 5 个真实混乱需求测试 skill 的实际行为，分两轮：首轮测试暴露问题 → 修订 → 回归验证。

测试方式：每个用例交给一个独立上下文的 agent，让它只读 SKILL.md（及引用文件）后按规则扮演助手，产出指定轮次的回复，并附自评。这样测的是 skill 文本本身能不能约束住一个不了解设计意图的执行者。

---

## 一、首轮测试（3 例）

| # | 输入 | 类型 |
| :--- | :--- | :--- |
| 1 | 「我想弄个工具管理我下载的那些电影，乱七八糟的……NAS 上也要能用，朋友说用 docker 部署，你觉得呢」 | 软件功能 |
| 2 | 「帮我写个报告……要跟老板汇报，得显得有成果一点，别太长也别太短，下周要用」 | 文档报告 |
| 3 | 「我每天要从三个网站上扒价格，现在手动太烦了，写个脚本自动跑，存到表格里，有问题告诉我」 | 脚本工具 |

### 通过的部分

三个用例都做到了这几件事，说明核心设计是立得住的：

- **剥掉了手段**。用例 1 把「Docker」识别为朋友的建议而非已验证的结论，把四条要求归并成「你其实需要一个媒体服务器，不是自己写工具」。用例 3 把「写个脚本」剥成「每天固定时刻手里已经有一份价格快照」。
- **矛盾双列摊开**。用例 2 抓到了「显得有成果 vs 别太长」和「显得 vs 有」两层冲突。用例 3 抓到了更隐蔽的一处：「存到表格里」和「有问题告诉我」互相拆台——静默失败时表格只少一行，用户翻表未必发现。
- **建议里有真判断**。用例 1 建议砍掉订阅下载链路（描述里根本没提追新），用例 3 建议先做一个站再复制、先不上自动通知。都是对范围的实质收敛，不是泛泛而谈。
- **一次只问一个**。三例均只出 Q1，且都停在决策树的根节点（谁用 / 要老板做什么 / 表给谁做什么决定），没有插队问下游细节。
- **主动查证**。用例 1 实际联网核实了 Jellyfin、MoviePilot V3、MeiamSubtitles；用例 3 查了本机 Python 版本与已装依赖。都落在「事实归你，决定归用户」的守则上。

### 暴露的问题（6 条，全部修订）

| # | 问题 | 修订 |
| :--- | :--- | :--- |
| 1 | 「缺口」栏被当成问题清单，与「一次一问」打架 | 阶段一补「缺口栏是陈述，不是提问」，并规定超过五条只留最靠上游的三四条 |
| 2 | 置信度后的"缺什么"与缺口栏重复 | 规定置信度只写最关键的一个，其余进缺口 |
| 3 | 默认值写了但不知道写在哪 | 阶段二新增固定格式 `**默认（不问你，除非你要改）**：<值>`，明确它是唯一允许"不问就定"的出口 |
| 4 | 同一层多个高影响问题无裁决标准 | 阶段三新增排序原则：按「猜错的代价」，目标 → 边界 → 数据/结构 → 交互细节 → 措辞 |
| 5 | 建议条数无上限，与「短」冲突 | 限制不超过三条，其余宁可不写 |
| 6 | 编号规则缺失（示例直接从 Q3 起） | 规定从 Q1 连续编号；示例同步改为 Q1/Q2 |

### 另外补充的三条

- **选项互斥且穷尽**：混合情况（"电视和手机都用"）不能让用户在都不对的选项里硬挑，要么改问题，要么加"都有"选项。
- **查证的边界**：查到"足以判断这个问题的答案会改变什么"就停，不为建议而通读代码库；需求与本地项目无关时跳过查项目。
- **任务太小别硬走四段**：所有维度 ≤ 0.1 时直接动手。

### 首轮发现的、未采纳的建议

测试 agent 提了几条建议，评估后未采纳：

- **「首轮回复边界」写到阶段三**——已写入阶段一之前的总述，位置更合适。
- **「失败时我该查什么」写得过细**——现有「查什么、查到哪一步」已覆盖，再细就是过度规定。

## 二、回归测试（2 例）

### 用例 4：饮食记录（验证首轮修复项）

> 「我想搞个东西记录每天吃的东西，然后能看看我营养够不够，别太麻烦，我坚持不下来那种就算了」

五个检查点全部通过：

| 检查点 | 结果 |
| :--- | :--- |
| 缺口栏是陈述不是提问 | 4 条，全部名词短语，无问号 |
| 默认值行 | 使用了：`单用户自用、数据只存本机，不同步、不联网上传` |
| 编号 | Q1 |
| 建议条数 | 3 条 + 1 条「我不建议」 |
| 选项互斥穷尽 | A/B/C 用"只看…"限定，D 接住混合情况，E 兜底"说不上来" |

这一例还展示了 skill 想要的效果：它把「记录每天吃的东西」这个手段剥开，指出「每天记录」和「别太麻烦」本身冲突，并把「营养够不够」缩成三个可判断的项。Q1 直接问「你具体想确认哪一件事」——这是能改变整个记录方式的上游问题。

### 用例 5：小区二手交换（验证第二轮衔接）

> 第一轮：「我想给小区做个二手物品交换的东西……老人家也会用」
> Q1 回答：「其实主要是我自己用，我就是想把我家里那堆闲置处理掉，邻居顺手拿」

这一例专门测「答完之后做什么」里最难的第二种情况——**答案推翻了先前的读法**。结果正确：

- 明确说出错在哪：「错在主语：要清的是你家的东西，小区只是分发半径，不是服务对象。」
- 改了对应条目，不是只加一句补充说明：核心诉求、推断、老人的约束对象三处都更新了。
- 记了决策：`#1 决定：主用户＝你自己，邻居是接收方（意味着：账号、审核、公共运营、纠纷处理全部不做……）`
- 没有复述用户刚说的话，直接进入纠正 + Q2。
- 编号连续到 Q2。
- 新问题选得对：从「送还是卖」问起，因为账号、定价、交接、「能聊」降到什么程度全都挂在它下游。

### 回归测试仍暴露的、未修的点

测试 agent 提出「『影响最大』没有客观标准」。确实没有，也不该硬定——影响大小依赖具体场景，写死一套权重会比现在更糟。现有的「猜错代价」排序原则已经够用了。

另有「推荐答案的强度」没有标准（推荐得太强会引导回答）。这是有意留白：`interview-me` 的论证是"引导是对的，风险在附和而非引导"，本 skill 通过要求给出理由来对冲，不设强度上限。

## 三、结论

skill 的核心机制在五个不同类型的需求上都正常工作，且能约束住不了解设计意图的执行者。三个真正有价值的行为都验证出来了：

1. **能把手段从诉求里剥出来**，并对范围提出实质性的砍法，而不是顺着用户列的需求做加法。
2. **能发现描述内部的矛盾并双列摊开**，包括像「存表格 vs 通知我」这种不显眼的冲突。
3. **能在答案推翻读法时明确纠错**，而不是偷偷按新理解继续走。

已知局限：模糊度评分（五维 0.35 阈值）没有被实测到，因为五个用例都在首轮或第二轮就停了，没走到收尾判定。这一环只能在实际长时间使用中检验。
