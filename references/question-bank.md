# 问题库：按任务类型取问题

第三阶段不知道问什么时翻这里。**按需挑，不要当问卷照抄。**

每个问题后面标了「为什么值钱」——如果你想不出为什么，在这个具体场景里它就不值钱，跳过。

---

## 通用：任何需求都值得先问的四个

这四个命中率最高，优先在它们里挑第一个问题。

| 问题 | 为什么值钱 |
| :--- | :--- |
| **做完了你会怎么用它？** | 把"想要"拉回"使用场景"。很多人描述的是想象中该有的东西，不是真会用的东西。 |
| **现在这件事你是怎么解决的？** | 现有办法就是竞争对手。答案里通常藏着真实痛点，以及能不能"什么都不做"。 |
| **最晚什么时候要？** | 时间是最强的范围约束。急 → 只能砍功能；不急 → 有机会做对。 |
| **如果只能保留一件事，留哪件？** | 逼出真正的主次。用户列的五条需求，价值经常差一个数量级。 |

## 一、软件功能 / 应用

| 问题 | 为什么值钱 |
| :--- | :--- |
| 谁用？几个人？是你自己还是别人也要用？ | 决定要不要权限、多用户、并发。自用和团队用的差距比想象中大一整个量级。 |
| 数据从哪来？现在以什么形式存在？ | 数据源形态决定大半工作量。答"在几个 Excel 里"和答"有 API"是两个完全不同的项目。 |
| 数据量多少？一天几次操作？ | 100 条和 100 万条是不同的设计方案，但用户的描述一模一样。 |
| 第一次上线，有几个人能看到？ | 内部灰度还是直接对外，决定要不要做得稳、要不要回滚方案。 |
| 坏了会怎样？有人会受影响吗？ | 判断可靠性投入。没人受影响的话，粗糙版本先上是对的。 |
| 要不要和现有系统对接？哪个？ | 对接是隐藏工期黑洞，越早知道越好。 |
| 手机上必须能用吗，还是"顺便更好"？ | 这是最常见的伪需求，也最贵。 |

---

## 二、脚本 / 小工具

| 问题 | 为什么值钱 |
| :--- | :--- |
| 多久跑一次？手动还是定时？ | 一次性和常态化是两种东西。一次性的别做错误处理和日志。 |
| 出错时你希望它怎么办？停下等你，还是继续跑完再报？ | 批量工具的事故大多来自"出错了但没停"。 |
| 失败重跑会不会产生重复数据？ | 幂等性是脚本最常被忽略又最贵的一环。 |
| 输入格式稳定吗？会不会变？ | 稳定的可以硬编码，会变的要留配置。判断错了就是返工。 |
| 跑在哪？本机、服务器、还是 CI？ | 决定能不能装依赖、有没有网络、权限如何。 |
| 输出给谁看？人读还是机器读？ | 决定格式：表格给人，JSON 给下游。 |

## 三、文档 / 报告

| 问题 | 为什么值钱 |
| :--- | :--- |
| 读者是谁？他们读完要做什么？ | 读者决定深度、术语密度、要不要背景铺垫。 |
| 多长？有没有页数或字数限制？ | 有硬约束时，取舍早做比晚砍省事。 |
| 是要说服人，还是记录事实？ | 说服要论证结构；记录要覆盖完整。写法完全不同。 |
| 有没有现成的同类文档可以参考？ | 有就给路径当规格，比用文字描述十遍都准。 |
| 什么时候要？谁审？ | 审稿人是谁，往往决定该按什么口径写。 |
| 里面有没有不能写出去的内容？ | 涉密、涉客户，越早问越好。 |

---

## 四、排查 / 诊断

| 问题 | 为什么值钱 |
| :--- | :--- |
| 什么时候开始的？之前动过什么？ | "之前动过什么"命中率极高，尤其系统类问题。 |
| 每次都能复现，还是偶尔？ | 必现和偶发是两条完全不同的排查路线。 |
| 最近改了什么？装了什么？更新了什么？ | 时间相关性是最便宜的线索。 |
| 正常的时候是什么样？ | 没有基线就无法判断"修好了"。 |
| 影响多大？能忍多久？ | 决定是先止血还是先找根因。 |
| 已经试过什么？结果如何？ | 避免重复劳动，也能看出之前的方向对不对。 |

---

## 五、设计 / 创意

| 问题 | 为什么值钱 |
| :--- | :--- |
| 给谁看？第一眼要传达什么？ | 没有目标观感就没有对错，评审会变成主观拉扯。 |
| 用在哪？尺寸、媒介？ | 印刷和屏幕、横幅和头像，构图逻辑完全不同。 |
| 有没有必须遵守的品牌规范或已有素材？ | 有素材就沿用，别重造。 |
| 你喜欢和讨厌的参考各给一个？ | 两个参考比十句形容词准得多。 |
| 要多快出？要不要给几版挑？ | 决定是做一版精修，还是三版粗坯。 |

---

## 六、调研 / 选型

| 问题 | 为什么值钱 |
| :--- | :--- |
| 结论用来做什么决定？ | 决定调研深度。"了解一下"和"下周要拍板"差十倍工作量。 |
| 有没有硬约束（预算、必须开源、必须自托管）？ | 硬约束能砍掉大半候选。 |
| 现在用的是什么？为什么想换？ | 迁移成本常常大于换来的收益，先确认值不值。 |
| 最看重哪一项？性能、成本、维护、生态？ | 多目标等于没目标，逼出排序。 |
| 结论要什么形式？对比表、推荐、还是详细评估？ | 形式不对就要重做。 |
| 什么时候要结论？ | 有时间盒才能决定调研到哪停。 |

## 反问题：听到这些就换问法

用户给出下面这类回答时，别接受、别记录，改成追问。

| 用户说 | 追问 |
| :--- | :--- |
| "要可扩展" | 现在多少量？预计涨到多少？什么时候涨到？ |
| "要健壮 / 稳定" | 出问题能接受多久停？谁能重启？ |
| "按最佳实践来" | 如果不用向任何人交代，你实际想要什么？ |
| "你看着办" | 我倾向 A，因为 <理由>。选 B 的代价是 <代价>。用 A 吗？ |
| "越快越好" | 一周能做的最小可用版本，和一个月能做好的版本，你要哪个？ |
| "先做出来再说" | 先做哪一部分？哪部分可以完全不做？ |
| "差不多就行" | 哪一部分可以粗糙，哪一部分不能？ |
| "和别人一样" | 哪个"别人"？给我一个具体的东西。 |
| "预算不是问题" | 那时间呢？或者：如果只能投一个人一个月，你选哪个方向？ |
